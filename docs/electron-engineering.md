## 背景

当前架构：

```
Next.js(TS, 静态导出) → frontend/next/out
Electron 壳(JS, main.js) → 加载 out + spawn 后端 exe
Python 后端(FastAPI, PyInstaller) → 127.0.0.1:8000
数据: 环境变量 WECHAT_COLLECTOR_DATA_DIR 约束(开发=项目根data, 打包=exe旁data)
```

已做对的部分：`contextIsolation` + `nodeIntegration:false`、后端独立进程（天然隔离）、看门狗防孤儿后端、后端 DPI 处理、CSP 生产严格注入 ✅、release-it 一键发版 + 多文件版本同步 ✅。

## 一、低成本必修（4 项，1 项已完成）

### 1. 单实例锁（Single Instance Lock）🔴
- **缺口**：重复双击 exe 会开多个窗口 + 多个后端抢 8000（当前仅端口层复用兜底，应用层未拦截）
- **做法**：`app.requestSingleInstanceLock()`，拿不到锁则退出并 `app.focus()` 已有实例
- **预估**：约 10 行

### 2. 渲染进程崩溃处理 🔴
- **缺口**：`render-process-gone` / `did-fail-load` 无监听，崩溃即白屏，无提示无恢复
- **做法**：监听崩溃事件 → 弹错误页/对话框 → 可选自动 reload；`unresponsive` 提示
- **预估**：约 30 行 + 简单错误页面

### 3. 窗口状态记忆 🟡
- **缺口**：每次启动固定 1180x760 居中
- **做法**：退出时保存 `win.getBounds()`，启动时恢复（写 userData 下 json）
- **预估**：约 20 行

### ~~4. CSP 安全头~~ ✅ 已完成（2026-08-26，V4.0.1）
- 生产：静态导出严格策略（`default-src 'self'` + API 白名单 + frame/object 全禁）
- 开发：不注入（Next HMR 依赖 eval，注入会引发重复加载，属正常现象）

## 二、近期发现的补充项（V4.0.1 后新增）

### ~~8. 打包产物体积瘦身~~ ✅ 已完成（2026-08-26，V4.0.1）
- release 1.1GB → 548MB：排除 torch(365M)/pandas/matplotlib/llvmlite/numba/Pythonwin；onnxruntime 改为只收 DLL(不再拖 quantization→torch)
- 冒烟验证：启动/health/OCR引擎就绪 均正常

### 9. 统一日志 / 诊断 🟢
- **现状**：主进程 main.log、后端 console、前端 console 三处分散，排查问题时来回切
- **做法**：壳侧引入统一结构化日志（时间戳 + 来源标记），渲染错误透传主进程落盘

### 10. 开发模式端口冲突防护 🟢
- **现状**：dev 下重复跑 `npm run dev` 会起多个 python 抢 8000（后端 reload 阻塞）
- **做法**：dev 脚本检测 8000/3000 已占用则提示先清理；或 backend 启动失败给明确提示

### 11. OCR 引擎启动预热 🟢
- **现状**：health 秒回但 OCR 后台线程加载（读取数/评论功能要等引擎就绪）
- **做法**：Electron 等待 health + ocr-ready 双就绪再显示主界面（或显示"引擎加载中"过渡屏）

### 12. 数据库一键备份 🟢
- **现状**：data 文件夹就是全部数据，迁移靠手动复制
- **做法**：设置页加「备份数据」按钮 → 复制 data/ 到带时间戳的备份目录（或导出单文件）

## 三、中期方向（按分发/使用场景决定）

### 5. 自动更新（electron-updater）
- 价值：发版后用户自动更新，免手动重新下载
- 依赖：需要发布渠道（GitHub Releases / 私有服务器）；内部小范围使用可后置

### 6. 崩溃监控 / 上报
- 现状：仅主进程 main.log
- 做法：render-process-gone 等事件 + 后端异常统一上报（crashReporter 或轻量事件收集）

### 7. 自动化测试 / CI
- 现状：零自动化，回归靠手动点
- 做法：Playwright 驱动 Electron 冒烟测试（页面加载/后端拉起/基本操作），可挂 GitHub Actions

## 四、可选架构演进（考虑过，暂不执行）

### electron-vite 迁移评估
- **它能给的**：主进程 TS 化、构建链统一（主/preload/渲染一个 CLI）、dev HMR 更好、打包体积更小
- **代价**：渲染层要从 Next.js 换 Vite+React —— 三个页面 + 共享组件需重建
- **结论**：当前 Next App Router 本身即 TS 体系、且更主流；除非未来要大幅减体积/统一构建链，否则不迁移。如真要尝试，可在独立分支做原型对比。

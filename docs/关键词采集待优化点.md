# 关键词采集待优化点（feature/keysearch）

> 状态：程序正式运行中，此文档仅记录待优化项，不涉及代码改动。
> 涉及流程：`gzh_query_page_init` → `gzh_query_page_article_loop`（公众号查询页文章列表循环）

---

## 待优化点 1：关键词采集的筛选设置

### 现状
- 关键词查询采集 = 按关键词搜索公众号文章列表 → 识别文章点位（判定：文本含"阅读"+数字 且 灰字白底）→ 遍历**全部**点位，逐一点击采集（`article_data_collect(collect_type=1)`）。
- 当前没有任何筛选条件：识别到的文章点位**无条件全采**。

### 期望（待确认/设计）
增加"筛选设置"，让用户决定哪些文章值得采集，候选维度：

| 维度 | 说明 | 示例 |
|---|---|---|
| 标题关键词 | 文章标题包含/排除指定词（OCR 结果里标题行做匹配） | 标题含"政务"才采 |
| 阅读量范围 | 阅读数在 [min, max] 内才采 | 阅读 ≥ 1000 |
| 点赞量范围 | 点赞数与阅读类似（需点位支持提取赞） | 点赞 ≥ 10 |
| 发布时间范围 | 见待优化点 2（时间范围） | 只采近 30 天 |

设计约束（供参考）：
- 筛选应作用于"遍历点位点击"之前（`_extract_article_points` 之后、`mouse_click` 之前），不达标点位跳过采集。
- 前端采集弹窗需增加筛选设置区（关闭/开启 + 各条件输入），随 payload 传入。
- 后端 `gzh_query_page_article_loop` 增加筛选参数（或一个筛选配置对象）。

### 前置依赖
- 点位数据里目前只有 `reads`（阅读数）；标题/赞需要 OCR 结果里额外提取，或点位改用"文章行"（标题行）作为点击对象。

## 待优化点 2：关键词采集兼容时间范围

### 现状
- `gzh_query_page_article_loop` 已接收 `date_start` / `date_end` 参数（与 `article_list_wait_stable` 签名一致），但**尚未使用**（点击采集时不做任何时间判断；用户此前指示"不需要时间判断"）。
- 文章点位识别已**取消时间解析**（`_TIME_RE`/`_match_article_struct`/pass B 配对均已删除，判定简化为"阅读+数字"），点位对象里 `time=None`。

### 期望（待确认/设计）
关键词采集兼容时间范围，即：按 `date_start`/`date_end` 过滤文章点位，范围外的文章跳过采集。

已知现实约束（历史踩坑记录）：
- 公众号查询页的时间格式多样且 OCR 噪声大，常见形式：
  - `2025/3/3`、`2022/10/9`（OCR 可能漏斜杠：`202210/9`、`2022109`）
  - `3/5`、`5`（月/日、日）
  - `n个月前`、`n天前`、`n小时前`（OCR 可能把"个"识别成"人"：`3人月前`）
  - 时间与阅读可能**拆成两条 OCR 条目**（需按同一行配对，行判定阈值 = box 高度 1/3）
- 相对时间（n个月前）需按"当前日期 - n"换算成绝对日期再与范围比较。
- 参考实现：`article_list_wait_stable` 的日期范围逻辑（时间点位落范围→继续/过范围→累计停止），但关键词页格式不同，需适配。

### 建议实现路径（供后续开发）
1. 恢复/重做：从 OCR 提取文章行时间（时间条目 + 阅读条目按行配对，或连读文本直接解析），转换 `n个月前/天前/小时前` → 绝对日期。
2. `gzh_query_page_article_loop` 遍历点位时：解析点位时间，`date_start`/`date_end` 范围外跳过点击采集。
3. 注意：恢复时间解析后，`_extract_article_points` 的判定应"阅读为必需、时间为可选"（时间解析不到就按"不在范围可采"或"跳过"策略，需与用户确认兜底行为）。
